description: 束からまとめて一気に入れる（1ブランチ・1PR。設計先出し → 実装 → 最後に検証1回）
---

このチャットは**まとめ取り込み**。効率を優先して、1本のブランチに複数件を入れる。

まず @docs/roadmap.ja.md の候補表と、触る束の「済」の節を読む。そのあとこの順で動く。

1. **束ねる。** 対象は**同じ束**（同じコードを触るもの）から選ぶ。別の束を混ぜるのは
   「同じ所を2回読む」ことになるので、明示的に頼まれていなければしない。
   目安は**実装3〜5件**（P1級1件＋同じファイルを触る小物2〜4件）。
2. **設計を先に1回だけ出す。** 各件について「何を作る／どこに書く／**機械の突き合わせは
   何か**／やらないこと」を数行で並べる。**承認は待たずに実装に入る**（止めてほしい場合は
   「設計だけ」と言われている）。ここを飛ばすと、4件書いたあとに2件目の方針が変わって
   文書とロードマップまで書き直しになる。
3. **実装は1件ずつ完成させる。** コード＋**その機能の試験**まで書いて次へ。各件の終わりで
   `npm run build`（tsc）を通す＝型の壊れを次の件に持ち込まない。**どの時点で切れても
   ツリーは PR にできる**状態を保つ。
4. **検証は最後にまとめて1回。** フル試験・触った CI ステップの実走・`check-docs.mjs`・
   サイトの build。途中で毎回フル試験を回すのは時間の無駄（1回 70 秒 × 件数が消える）。
5. **文書・ロードマップ・サイトは最後にまとめて。** 実装が全部固まってから書く（先に
   書くと必ず書き直しになる）。ロードマップは**済に落とす＋候補を3〜5件補充**まで。
6. **入りきらないと分かったら、そこで区切る。** 黙って続けない。「入ったもの／入れなかった
   ものと理由／次の1手」を書いて、**その時点で PR を締める**（残りは候補表に残す）。

守るものは普段と同じで、速さのために省かない:

- **機械の突き合わせを省かない**（新しい資産には必ず「嘘をつけない仕掛け」を付ける）
- **試験を後回しにしない**（その件の試験を書かずに次へ行かない）
- **「あとで直す」前提のコードを入れない**
- コミット / Push はしない。終わりに**コミットタイトルと PR 本文**を必ず渡す

分けるのはこの3つだけ（このときは理由を言って別ブランチにする）:

- 互換を壊す変更と、壊さない変更
- 別の束（同じファイルを触らないもの）
- レビューの読み手が違うもの（枠組みの契約 ↔ 文書だけの直し）

合図の言葉:

| 言われたら | やること |
| --- | --- |
| 「一気に」「まとめて」 | この手順に入る |
| 「設計だけ」 | 2 で止めて、承認を待つ |
| 「締めて」 | 実装を止めて 4 → 5 → 報告（いま入っているぶんで PR にする） |
