# AI への頼み方

hatake は AI が読み書きしやすいように作ってある（[AI に書かせる](/ai)）。それでも**AI が決められないこと**が残る ── 業務の言葉と、業務の決めごとだ。

| AI が決められる | 人が決める |
| --- | --- |
| 画面の種別・キーの書き方・型・警告の直し方 | **業務の言葉**（項目名・画面名・ボタン名） |
| 一覧に絞り込みを付ける、桁区切りを付ける（好みは `advise` が言う） | **業務の決めごと**（上限件数・締めの規則・消させない・確認の文） |
| バックエンドが返すべき形（`openapi` / `types`） | **どこからデータが来るか**（Repository の名前、無ければ「まだ無い」） |
| 役割で出し分ける書き方 | **役割の名前**（`manager` なのか `sales_manager` なのか） |

この4つを渡さないと、AI は**それらしい嘘**を書く。「顧客名」で通ると思って書いたら現場は「先方名」だった、という類の嘘は、動くので気づけない。

## 最低限の3つ

急いでいるなら、これだけ書けば着手できる。

1. **誰が・何のために使う画面か**（「営業が、受注を探して状態を直す」）
2. **扱う項目と、その業務の言葉**（「受注番号・顧客名・受注日・状態・金額」）
3. **守る決めごと**（「出荷済は直せない」「一括では消させない」）

決まっていないものは「**決まっていない**」と書く。空白で渡すと AI が埋めてしまうが、「決まっていない」と書けば、AI はそこを `TODO` にして聞き返す。

## 埋めるだけのテンプレ

```
## やること
（1文。例: 受注を探して、状態を直せる画面を作る）

## 使う人
（役割の名前 / 例: sales（営業）, manager（承認者）。役割で出し分けるなら、アプリが配っている名前そのまま）

## 画面でやること
- 探す:（何で絞れるか。例: 受注番号・顧客名・受注日の範囲・状態）
- 見る:（一覧に出す列。例: 受注番号・顧客名・受注日・状態・金額）
- 直す:（何を直せるか。例: 状態だけ / 全部 / 直せない）
- 押す:（ボタンと、押したら何が起きるか。例: 一括承認＝選んだ行をまとめて承認）

## データの出どころ
（Repository の名前 / 例: orderRepository。まだ無ければ「まだ無い（形はそちらで出して）」）

## 業務の決めごと
- （例: 出荷済の受注は直せない）
- （例: 一括承認は1回 20 件まで）
- （例: 削除は使わない。取消の印を立てる）

## 決まっていないこと
- （例: 却下の理由の選択肢は未定）

## 終わりの判定
（例: validate が警告ゼロ・run のシナリオが通る・explain を読んで意図と合っている）
```

**「終わりの判定」を書くのが一番効く。** これが無いと AI は「動いたつもり」で止まる。hatake なら判定が道具で書ける ── それが次の節。

## 終わりの判定に使えるもの

| 言い方 | AI が回す道具 | 何が保証されるか |
| --- | --- | --- |
| 「`validate` を警告ゼロで通して」 | `hatake validate --warn-as-error` | 書いたのに効かない書き方が無い |
| 「`run` のシナリオを通して」 | `hatake run --scenario`（[試す](/testing)） | **その値でその答えになる**（計算・必須・押せる） |
| 「`explain` を貼って」 | `hatake explain` | 人が**定義を読まずに**意図を確かめられる |
| 「`advise` を1回かけて、当てるものは相談して」 | `hatake advise` | 書いていない所（好み）を見落とさない |
| 「`diff` で壊していないことを見せて」 | `hatake diff`（改修のとき） | 既存の呼び出し側を壊していない |

「動きました」ではなく「**この5件のシナリオが通りました**」で報告させる。定義ファーストの値打ちは、判定が定義から作れることにある。

## ケース別の型

### A. 新しい画面を作る

上のテンプレそのまま。加えて**近い画面**があれば必ず言う（「顧客マスタと同じ作りで」）。AI は例を写して直すのが一番速く、一番外れない。

```
受注照会の画面を作って。顧客マスタと同じ作りで。
探すのは受注番号（部分一致）・顧客名（部分一致）・受注日（範囲）・状態（未出荷/出荷済）。
一覧は受注番号・顧客名・受注日・状態・金額（¥ 桁区切り）。
行から明細を開く。明細は直せる（出荷済は直せない）。
Repository は orderRepository。
終わりの判定: validate 警告ゼロ・run の下書きを作って通す・explain を貼る。
```

### B. 既にある画面を直す（改修）

**変える前と後を書く。** 「良くして」ではなく「いまこうで、こうしたい」。

```
order_search（受注照会）を直して。
いま: 一覧に金額が出ていない。
こうしたい: 金額を出す（¥ 桁区切り・右寄せ）。合計は出さない。
決めごと: 列は増やすが、絞り込みは増やさない（画面を広げたくない）。
終わりの判定: diff で「壊す変更なし」・explain --diff で変化を1行で貼る。
```

改修では **`diff` と `explain --diff`** を必ず要求する。前者は「API を壊したか」、後者は「画面がどう変わったか」を言う ── **別の道具**なので両方。

### C. 不具合を直す

**「期待」と「実際」を分けて書く。** hatake ではこれがそのままシナリオになる。

```
order_entry の小計が合わない。
実際: 取消の行も足されて 1,000 円になる。
期待: 取消の行は外して 200 円。
再現: 明細2行（鉛筆 2×100、ノート 1×800 で取消）。
終わりの判定: この形を run のシナリオに入れて、通ることを見せて。
```

再現手順を**値で**書くと、AI はまず失敗するシナリオを書き、直してから通す（テストファースト）。「たまに変」だけでは何も始まらない。

### D. アプリに繋ぐ・バックエンドの形が要る

```
order_search を実際に動かしたい。
Repository は REST（/api/orders）。認証はヘッダに Bearer。
バックエンドはまだ無いので、返すべき形を出して。
終わりの判定: refs で要る登録を全部並べて・wire で配線の下書き・openapi を出す。
```

「まだ無い」を言うのが大事。**定義から契約が出る**ので、サーバ側の実装が後でも進められる。

### E. DSL に無いことをやりたい

```
消費税の計算を項目に入れたい（税率は案件で変わる）。
DSL に無いなら、プラグインで足す形を提案して。フレームワーク本体は直さない。
終わりの判定: 定義側の書き方（op の名前と引数）と、登録するコードの両方を出して。
```

hatake の原則は**本体を直すよりプラグイン**。頼むときにそう言えば、AI は正しい側に寄る（[AI に書かせる](/ai) の原則もそうなっている）。

### F. レビュー・棚卸し

```
この定義（貼る）をレビューして。
見てほしいのは: 誰が何を開けるか・押しても何も起きないボタン・一括の安全（確認と上限）。
終わりの判定: explain --review を貼って、直すべきものは理由付きで挙げて（直すかは相談）。
```

## 頼み方のアンチパターン

| 言い方 | 何が起きるか | 代わりに |
| --- | --- | --- |
| 「Flutter で受注画面を書いて」 | Widget を書き始める（この枠組みの意味が消える） | 「**定義で**受注画面を書いて」 |
| 「いい感じにして」 | それらしい嘘（現場に無い項目名）が混ざる | 業務の言葉を渡す。無ければ「決まっていない」 |
| 「テーブル定義を渡すから作って」 | DB の列がそのまま画面になる（業務の画面にならない） | **誰が何をするか**を先に書く |
| 「全部の画面を作って」 | どれも半分になる | 1画面ずつ。近い画面を「同じ作りで」と言う |
| 「テストも書いて」（丸投げ） | 通ることしか確かめないテストが生える | 「**期待をこう書いたシナリオ**を通して」 |
| 「役割は適当に」 | 画面は出るのに誰にも見えない | アプリが配っている役割名そのまま渡す |

## 人が最後に見るもの

AI が書いた YAML を1行ずつ読む必要はない（読めるように作ってあるが、読むのは大変だ）。**読み返し**を読む。

```bash
npx hatake explain order_search.yaml
```

「この画面は何ができて、何ができないか」が業務の言葉で出る。**そこに書いてあることが意図と違えば、定義が違う。** 逆に言えば、頼むときの文とこの出力を見比べられるように頼めばよい ── それが「終わりの判定」を書く意味だ。
