# 言ったことを残す

AI に「受注照会の画面を作って。探すのは受注番号と顧客名で、承認ボタンを押したら選んだ行をまとめて確定にする」と頼めば、定義は出てくる。出てきた定義は動く。**動くから気づけない**のが問題で、あとから3つ困る。

| 困ること | いま何が起きているか |
| --- | --- |
| 言ったのに入っていない | 頼んだ絞り込みが1つ落ちている。画面は出るので、使う日まで分からない |
| **言っていないのに入っている** | 頼んでいない列やボタンが増えている。AI に書かせると必ず出る |
| 未定のはずが決まっている | 「却下の理由は未定」と言ったのに、選択肢が3つ書かれている |

## 設計書をコードから生成しても、これは消えない

hatake は定義から人の言葉を出せる（[explain](/ai)）。これは**生成物なので古くならない**設計書で、値打ちはある。それでも上の3つは消えない ── **言ったことが定義に書いていない**から。意図・理由・決めた人・決まっていないことは、どこにも残っていない。

だから残すのは1枚だけ。**言ったこと**を機械可読な形で置く。

## 意図の1枚

定義の隣に `<画面id>.intent.yaml` を置く。

```yaml
intent_version: "1.0"
page: order_search

asked:                                  # 人が言ったこと（原文のまま）
  - id: R1
    text: 受注を受注番号・顧客名・受注日の範囲で探せる
    covers: [filter:orderNo, filter:customer, filter:orderDate]
    by: 田中
    at: "2026-09-08"
  - id: R2
    text: 承認ボタンを押したら approveOrders を呼んで、選んだ行をまとめて確定にする
    covers: [action:approve]

decisions:                              # 業務の決めごと（理由つき）
  - id: D1
    text: 出荷済の受注は直せない
    why: 倉庫の締めが先に走るため
    covers: [field:status]

undecided:                              # 決まっていないこと
  - id: U1
    text: 却下の理由の選択肢は未定
    covers: [field:rejectReason]

acceptance:                             # 終わりの判定
  - validate --warn-as-error
  - run --scenario order.scenario.json
```

**`text` は要約しない。** 人が言ったまま置く ── 要約した時点で読んだ側の解釈が混ざり、それが言った言ってないの正体だから。

**`covers` が肝。** 「その要求が定義のどこに落ちたか」を指す。ここがあるから機械が突き合わせられる。

**「決まっていない」を空欄と区別して持つ。** 空欄は「まだ聞いていない」と「聞いたけど未定」を区別できない。`undecided` に書いてあれば、あとで誰かが決めたときに機械が気づける。

## 突き合わせる

```bash
npx hatake trace order_search.yaml
```

```
order_search: 要求 6 件 / 定義の相手 12 件
言ったのに入っていない（1 件）:
  ・R3「却下の理由を選べる」が指している field:rejectReason は定義にありません＝言ったのに入っていない、か、名前が違います。
未定なのに決まっている（1 件）:
  ・U1「却下の理由の選択肢は未定」は未定のはずですが、定義には field:rejectReason が在ります＝誰かが決めています。
由来の無い定義（2 件）:
  ・column:memo は、どの要求からも来ていません。
  ・action:export は、どの要求からも来ていません。
終わりの判定:
  ・validate --warn-as-error
  ・run --scenario order.scenario.json
```

一番効くのは**由来の無い定義**。頼んでいない列やボタンが増えているのは、レビューで一番見つけにくい（動くので）。

| 言うこと | 落とすか |
| --- | --- |
| 言ったのに入っていない（指す相手が定義に無い） | **落とす**（確かに食い違っている） |
| 未定なのに決まっている | **落とす** |
| 由来の無い定義 | 言うだけ |
| どこに落ちたか書いていない要求・人が見ていない下書き | 言うだけ |

**落とすのを2つに絞ったのは、途中から始められるようにするため。** 既にある定義に意図を後から書き始めると、最初は全部が「由来の無い定義」になる。そこで落とす道具は、1日で使われなくなる。全部を落としたいときは `--require-intent`（CI に置くときはこちら）。

## AI に読ませたものを、人が確かめる

指示文から AI が起こした要求は `source: ai-draft` の印を付ける。**AI がこう読んだ**という下書きで、人が見て `confirmed: true` にするまで未確認のまま。`trace` はそれを「人が見ていない下書き」として挙げる。

```yaml
  - id: R7
    text: 却下したら理由を残す（AI が会話から読み取った）
    covers: [field:rejectReason]
    source: ai-draft
```

**要求を定義から生成してはいけない。** 生成すれば必ず一致するので、突き合わせが何も言わなくなる。ここは規則として決めてある。

## 言わないこと

`trace` が言うのは**対応の有無**だけ。「意図どおりか」は言わない ── それは定義を読み返して（[explain](/ai)）人が決めること。機械が「意図どおりです」と言い出したら、その時点でこの仕組みは嘘をつく側に回る。

言った言ってないが**完全に消えるわけでもない**。`text` は人の言葉なので、解釈の幅は残る。消えるのは「入っていない／勝手に入っている」で、そこは機械が確実に言える。

## 頼むときの型と同じもの

[AI への頼み方](/asking)の「埋めるだけのテンプレ」は、そのままこの1枚の入力になる。テンプレの「やること・画面でやること・業務の決めごと・決まっていないこと・終わりの判定」が、`asked` / `decisions` / `undecided` / `acceptance` に順に落ちる。**頼み方を決めておくと、設計書が副産物になる**。
