# プロジェクト概要を先に作る

hatake は定義を書けば画面が出る。雛形を出して項目名を並べれば、その日には動くものが見える。**いきなり書ける**のがこの枠組みの売りだ。

けれど、いきなり書いていいのは**何を作るかが決まっているとき**だけ。決まっていない状態で書き始めると、動く画面ができてから作り直すことになる。そして AI に書かせるほど、この失敗は速く大きくなる ── AI は決まっていないことを聞かずに、**書ける方に倒す**からだ。

| 決めていなかったこと | 出てくるもの | 気づくとき |
| --- | --- | --- |
| このマスタは直せるのか | 編集ボタンと入力フォームが付いた画面 | 現場に見せたとき（「これ購買部のシステムで入れてます」） |
| 「取引先」と呼ぶのか「顧客」なのか | 画面ごとに `customer` と `partner` が混ざった定義 | 画面が10枚を超えたあたり |
| 項目名の付け方 | `order_date` と `orderDate` が同居した API | バックエンドと繋ぐとき |
| 誰が押していいボタンか | 誰でも押せる CSV 出力 | 監査で聞かれたとき |

どれも**定義としては正しい**ので、検証も警告も何も言わない。書いていないことは検査に出てこない。だから先に決める。

## 先に決めるのは5つ

多くはない。1時間で埋まる。

| 決めること | 何を書くか | 決めないと |
| --- | --- | --- |
| **何の業務か** | 1〜3行。「卸売の受注。営業が電話で受けた注文を入れて、出荷指示まで出す」 | 画面の粒度が人によって変わる |
| **使う人と置かれ方** | 「営業10人・事務所の PC」「出荷担当・倉庫のタブレット・手袋のまま触る」 | ボタンの大きさも一覧の件数も決まらない |
| **できないこと** | 「商品マスタは購買部の別システムが正。こちらからは直せない」「締めたあとの受注は直せない」 | AI が書ける方に倒す（上の表の1行目） |
| **データの出どころ** | Repository の名前と、その向こうに誰が居るか（「商品マスタ＝購買システムの REST・持ち主は購買部」） | 繋ぐ日まで「まだ無い」が見えない |
| **言葉** | 業務の言葉と、定義に書く名前の対（「取引先 → `partnerCode`」）。**呼ばない言い換え**も | 画面ごとに字が揺れる |

3番目の「**できないこと**」がいちばん抜ける。仕様書は普通「できること」を書く紙なので、書く欄が無いのだ。けれど画面を作る側にとっては、できないことのほうが強い制約になる。

## 読み物で終わらせない

ここまでを Word や Wiki に書いて終わりにすると、3か月後に誰も読んでいない。**機械が読める1枚**に落とす。定義の隣に `hatake.project.yaml` を置く。

```yaml
project_version: "1.0"

system:
  what: 卸売の受注。営業が電話で受けた注文を入れて、出荷指示まで出す。
  users:
    - 営業（10人・事務所の PC）
    - 出荷担当（倉庫のタブレット。手袋のまま触る）
  premises:
    - 商品マスタは購買部の別システムが正。こちらからは直せない（照会だけ）。
    - 締めは月末。締めたあとの受注は直せない。
  external:
    - name: productRepository
      what: 商品マスタ（購買システムの REST）
      owner: 購買部

glossary:
  - term: 取引先
    field: partnerCode
    avoid: [顧客, 得意先]
    note: 社内の帳票が全部「取引先」なので、画面もそう呼ぶ

naming:
  page: snake_case
  field: camelCase
  role: snake_case
  suffix:
    date: Date
```

読み返すのはこれ。

```bash
npx hatake project
```

置いておけば、道具は**渡さなくても読む**（定義の隣にあれば拾う）。

## 決めたことが、実際に守られる

概要を紙で持っているだけなら「読んでね」で終わる。1枚に落とすと、**そのうち一部は機械が突き合わせられる**。

```bash
npx hatake advise page.yaml --project hatake.project.yaml
```

```
# page.table.columns.1 [project-glossary-word]
  こうなる: ラベル「顧客コード」に「顧客」が入っています。案件の決めごとでは「取引先」と呼びます（社内の帳票が全部「取引先」なので、画面もそう呼ぶ）。
  書き足す: 「取引先」で言い直す。

# page.search.filters.0 [project-name-suffix]
  こうなる: `type: date` の項目 "orderDay" は、案件の決めごとでは名前を "Date" で終わらせます。
  書き足す: "Date" で終わる名前に直す（決めごと: naming.suffix.date = Date）。
```

これは**警告ではなく助言**（終了コードは変えない）。名前と言葉は「書いたのに効かない」ではなく案件の好みなので、CI を落とす種類の話ではない。

雛形も決めごとの形で出る。

```bash
npx hatake new crud --id order_entry --title 受注入力 --project hatake.project.yaml
```

## 縛れているものと、縛れていないもの

ここは正直に分けて見ておいたほうがいい。読み返し（`npx hatake project`）は毎回これを言う。

| 書いたもの | 誰が見るか |
| --- | --- |
| 用語（`glossary`）と名前の決めごと（`naming`） | **機械が定義と突き合わせる** |
| 何の業務か・使う人・**業務の前提**・外の相手 | **人と AI が読むだけ。** 誰も突き合わせていない |

つまり「商品マスタは直せない」と書いても、編集ボタンを足した定義は**普通に通る**。前提は定義に書きようがないので、機械には見えない。1枚に落とす値打ちは「守らせる」ことではなく、**読まれる場所に置く**ことにある。

## AI に渡す

MCP を繋いでいれば、最初に読む道具がこれになる（`hatake_project`）。順番は [AI に書かせる](/ai) にある。

繋がない使い方（Copilot・Cursor・ふつうのチャット）なら、`AGENTS.md` や `CLAUDE.md` に貼る断片を出せる。

```bash
npx hatake project --agents                      # 貼る断片（印つき）
npx hatake project --agents --merge AGENTS.md    # 2回目以降：印の中だけを差し替える
npx hatake project --agents --merge AGENTS.md --check   # CI：貼った節が古くないか
```

同じことを2か所に手で書くと、**前書きを直したのに設定ファイルが古い**が必ず起きる。だから1枚を正にして、貼る側は生成する。ブランチ名やコミット規約は前書きが持たない（定義に現れないものは機械が突き合わせられない）ので、そこは印の外に手で書いておけば、貼り直しても消えない。

貼ったあとに前書きだけ直すこともあるので、**古くなったら CI が言う**口も付けてある（`--check`。見るだけで書かない）。生成物なのに古い節が貼ってあると、AI はそれを読む。

## どこまでを hatake がやるか、も先に見る

概要を書くと、**hatake では書けないもの**が必ず混ざる。締め処理、承認フロー、認証、在庫の引当。これらは持たないと決めているので（[この Framework が持たないもの](/#この-framework-が持たないもの)）、**誰がやるかを先に決めておく**。

引ける表になっている。

```bash
npx hatake where 締め処理        # → 枠組みの外（なぜ持たないか＋画面側でできること）
npx hatake where 承認            # → 枠組みの外（画面は状態を見せるだけ）
npx hatake where 一覧の並べ替え   # → 定義で書ける（書くキーと次に引く道具）
npx hatake where --where outside # 持たないものの一覧
```

区分は4つ。`definition`（定義で書ける）／`plugin`（アプリ側に登録して足す）／`server`（サーバの担当）／**`outside`（枠組みの外）**。

`outside` と出たものは、前書きの `premises` に「**できないこと**」として書いておく。そうしておけば、AI が画面側に実装してしまうのを止められる（前書きは AI が最初に読む1枚なので）。

```yaml
premises:
  - 締めは会計システムが持つ。画面は「締めたら直せない」を見せるだけ。
  - 承認フローは社内の承認基盤。画面は状態を出して、次へ進めるボタンを置くだけ。
```

AI に「締め処理も作って」と頼むと、外だと言えないまま Dart を書き始める。これは**この Framework でいちばんやってほしくないこと**なので、道具の側でも止めるようにしてある（MCP なら `hatake_where`）。

## 画面ごとの話は、この次

案件の前書きは**案件ぜんたい**の話で、1回書けばあとは足していくだけ。画面1枚ごとに「何を言われたか」を残すのは別の紙になる。

| 紙 | 何が書いてあるか | いつ |
| --- | --- | --- |
| プロジェクト概要（`hatake.project.yaml`） | 何のシステムか・できないこと・用語・名前 | 案件の最初に1回 |
| 頼み方のテンプレ | この画面で何をするか・業務の決めごと・終わりの判定 | 画面を作るたび → [AI への頼み方](/asking) |
| 意図の1枚（`<画面id>.intent.yaml`） | 言われたこと・決めた理由・**決まっていないこと** | 画面を作るたび → [言ったことを残す](/design) |

## 作る順番

1. **プロジェクト概要を決める**（このページ。1時間）
2. **`hatake.project.yaml` に落とす**（`npx hatake project` で読み返す）
3. AI に渡す（MCP、または `--agents` で `AGENTS.md` に貼る）
4. 画面ごとに頼む（[頼み方のテンプレ](/asking)）→ 言われたことを残す（[意図の1枚](/design)）
5. 定義を書く・書かせる（[機能別の書き方](/dsl/)）→ 検証して読み返す（[AI に書かせる](/ai)）
6. 決めごとと突き合わせる（`npx hatake advise --project`）

## よくある失敗

- **概要を散文だけで持つ。** 読まれないし、機械も見られない。せめて用語と名前は表にする
- **用語を決めずに始める。** あとから揃えるのは、項目名を変える話になる（Repository・API・試験・他の画面の遷移まで直すことになるので、道具は自動で当てない）
- **前提を書かない。** 「できないこと」の欄が無い仕様書をそのまま渡すと、AI は書ける方に倒す
- **命名を後で揃えるつもりでいる。** 決めごとを1枚に書いておけば雛形から従うので、最初に書くほうが安い

書き方の詳しい所（キーの意味・機械が見る範囲・`--agents` の印）は [案件の前書き](https://github.com/ASIL-E-Hatake/hatake/blob/main/docs/guide/project.ja.md)。
