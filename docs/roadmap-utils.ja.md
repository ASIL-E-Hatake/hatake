# hatake ユーティリティ ロードマップ（日本企業向け）

日本企業の業務でだいたい毎回頼まれる「金額整形」「和暦」「全半角」「消費税」みたいなやつを、独自実装させずに hatake 側で用意しよう、という TODO。`＋` 印は畠山案に対して追加で入れたやつ（依頼でよく来る / よく見る要件）。

## 方針（大事なとこ）

- **まず受け皿を作る（P0）**。個別に足すと core が太るので、`ValidatorRegistry` と同じ登録式で `FormatterRegistry` / `ConverterRegistry` を用意する。DSL には開いた文字列キーを足す:
  - `format` … 表示整形（例 `{ field: amount, type: number, format: currency }`）
  - `normalize` … 入力の正規化（例 `{ field: name, normalize: [toHankaku, trim] }`）
  - `validators` … 既存のまま（レジストリに足すだけ）
- **層をまたぐ**: formatter は主にフロント表示だが CSV/帳票でバックも使う。converter / validator は主にバック（信頼できない入力）だがフロントの即時整形にも使う。→ 概念は `spec` に「名前」で定義し、各言語（Flutter / Java / TS）が実装する。
- **外部データが要るやつ**（祝日カレンダー、郵便番号→住所 等）は、データ源を持ち込まない。インターフェース（`HolidayCalendar` みたいな契約）だけ切って、実データは利用者 or opt-in パッケージ。Repository と同じ発想。
- **端数処理・税率・年度開始月・元号境界**みたいな「会社/制度で変わる」ものは、必ず**パラメータで external 化**（ハードコードしない）。
- マイナンバーなど**法的に取り扱い注意**なものは、保存禁止・マスク前提で、validator/mask のみ提供（値を溜めない）。

## 優先度

| Tier | 内容 | 狙い |
|---|---|---|
| **P0** | `format` / `normalize` キー + Formatter/Converter レジストリ（登録式・プラグイン） | 受け皿。以降を本体不変で足せる |
| **P1** | 金額 / 日付(標準+和暦) / パーセント / 半↔全角 / 数値パース(全角→半角) / 郵便番号(format+validator) / マスク | 最頻出。まずここで「おっ」となる |

## 設計の落とし所（実装時メモ）

- **1つの正規化された値 + 表示は formatter に寄せる**。DB/APIには生値、画面/CSVには formatter。往復（parse ⇔ format）はペアで用意（例 currency: `format(1234)→"¥1,234"` / `parse("¥1,234")→1234`）。
- formatter / converter / validator は全部**レジストリ + 開いた文字列キー**。組込を用意しつつ、利用者が上書き・追加できる（Flutter の `fieldBuilders`、`ValidatorRegistry` と同じノリ）。
- **ロケール/設定は引数で**。元号境界・年度開始月・税率・端数処理・祝日 は、コードに埋めずパラメータ or 契約経由。
- 各言語で**同じ名前**にする（`currency` / `warekiDate` / `toHankaku` …）。名前が揃ってれば「Flutter で `format: currency` して、Java の帳票でも同じ `currency` を使う」ができる。

## ステータス

- **P0（受け皿）… ✅ Flutter/Dart 実装済み**: `FormatterRegistry` / `ConverterRegistry`（`hatake_core`）、DSL に `format` / `normalize` キー（parser・DSLビルダー対応）。
- **P1（スターター）… ✅ 3言語完了**: formatter（currency / percent / date / wareki / postal / mask）、converter（toHankaku / toZenkaku / hiraToKata / kataToHira / trim / collapseSpaces / parseNumber）、validator（postalCode）。Material の表描画に `format` を配線済み（`format: currency` で `¥1,234,567` 等）。下の「TS / Java 横展開」「入力 normalize の自動適用」まで含めて P1 は完了。
- **TS / Java 横展開 … ✅ 完了**: 3言語（Flutter/Dart・TypeScript・Java）で同名・同挙動の Formatter/Converter/postalCode バリデータを実装・テスト済み。
- **入力 normalize の自動適用 … ✅ 完了**: Flutter は `CrudController.submitForm` が送信時に `FormNormalizer`（`normalize` チェーン）を自動適用してから validate/persist。TS は `normalizeRecord`、Java は `FormNormalizer`。
- **3言語コンフォーマンス・スイート … ✅ 完了**（[spec/conformance](../spec/conformance/)）。formatters/converters/validators は3言語、queries は TS/Java。
- **消費税 `computeTax` … ✅ 3言語実装＋conformance**（内税/外税・端数 floor/round/ceil）。`net/tax/gross` を返す。端数処理は事業者指定（ハードコードしない）。
- **税率別合計 `computeInvoice` … ✅ 3言語＋conformance**（適格請求書向け）。明細を税率ごとに合算し、**税率ごとに一度だけ**端数処理（明細ごとに丸めない）。`byRate`（税率昇順）＋ `total` を返す。
- **年度/四半期/半期 `fiscal*` … ✅ 3言語＋conformance**（開始月パラメータ）。
- **年齢/勤続 `ageAt`・`tenure` … ✅ 3言語＋conformance**（満年・年月）。
- **営業日 `isBusinessDay`/`nextBusinessDay`/`prevBusinessDay` … ✅ 3言語＋conformance**（土日＋**注入した祝日集合**。祝日カレンダーは外部データなので引数で渡す）。
- **元号算出 `eraOf` … ✅ 3言語＋conformance**（改元境界日で切替、明治より前は null）。元号テーブルは `wareki` フォーマッタと共有（単一の真実）。将来の改元はこの表を差し替えれば対応。
- **未**: 日付範囲バリデータ、法人番号/インボイス番号バリデータ、かな↔カナ以外の converter 追加分 等。

全体の進め方は [開発ロードマップ](roadmap.ja.md) を参照。
