## 業務システムって、どこも似たようなの作ってるよね

検索して、一覧出して、CRUD して、入力フォーム置いて、マスタメンテして…。会社が変わっても案件が変わっても、だいたい同じ画面を作ってる。しかも毎回ゼロから。入力欄並べて、テーブル組んで、ページング付けて、バリデーション書いて、API 叩いて…。

正直、これを毎回手で書くのがだるい。同じようなもんなら、**書くんじゃなくて「定義」しとけばよくない？** 定義さえあれば画面が出てくる、みたいな。

それをやるのが **hatake（畠）** 。

> 種（業務定義）を、畠（各言語のフレームワーク）に蒔いて、実り（アプリ）を得る。

## hatake は何なのか

ざっくり言うと、**業務画面を「コード」じゃなくて「業務定義（Definition）」から組み立てるためのフレームワーク一式**。特定の UI ライブラリの話じゃない。中心にあるのは言語非依存の **DSL 仕様** で、それを各言語のフレームワークが描画する、という構造になってる。

```
Business Definition (YAML / JSON / 各言語のDSL)
        │  Parser
        ▼
   PageDefinition          ← ここが唯一の正（言語に依存しない）
        │  Renderer（言語・デザインごとに差し替え可能）
        ▼
   UI
```

ポイントは真ん中の `PageDefinition` 。YAML で書こうが JSON で来ようが各言語のビルダーで組もうが、**内部では全部これ一個に収束する**。UI 側（Flutter とか）は、その定義をどう描くかを担当してるだけ。だから描画層も実装言語も後から差し替えられる。

## とりあえずこんな感じ

顧客マスタの CRUD 画面。書くのはこれだけ。UI のコードは一行も書かない。

```yaml
dsl_version: "1.0"
page:
  type: crud
  id: customer_master
  title: 顧客マスタ
  repository: customerRepository   # データ取得は実装者が用意する Repository をキーで解決
  key: id

  search:
    filters:
      - { field: name,   label: 顧客名,     type: text,   operator: contains }
      - { field: status, label: ステータス, type: select, operator: equals,
          options: [ { value: active, label: 有効 }, { value: inactive, label: 無効 } ] }

  table:
    rowActions: [edit, delete]
    columns:
      - { field: code,   label: コード,     sortable: true }
      - { field: name,   label: 顧客名,     sortable: true }
      - { field: status, label: ステータス, type: badge }

  form:
    sections:
      - title: 基本情報
        fields:
          - { field: code, label: コード, type: text, required: true,
              validators: [ { type: maxLength, value: 20 } ] }
          - { field: name, label: 顧客名, type: text, required: true }
```

これで、検索フォーム・一覧テーブル・ページング・行ごとの編集/削除・入力フォーム（バリデーション付き）が全部出てくる。「画面を組む」んじゃなくて「業務を書く」だけ。

## YAML がしんどければ他の書き方でもいい

同じ定義を JSON で持ってきてもいいし、型安全なコードビルダーで組んでもいい。どれで書いても **最終的にできる `PageDefinition` は完全に一致する**。ここはちゃんとテストで担保してる。

```
parse(YAML) == parse(JSON) == build(コードDSL)
```

要は「入り口は好きに選んでいい、出口（定義）は一個」って話。API から JSON で降ってきた定義も、手書きの YAML も、同じ土俵に乗る。

## なんで多言語でやるのか

業務システムって Flutter だけで作るわけじゃない。Java のサーバサイドで画面出すこともあるし、TypeScript のフロントもある。でも

**「業務が似てる」のは言語に関係ない**

なら、仕様（種）は共通にして、各言語は「その種を育てる畠」として用意すればいい。

- **spec** … 言語に依存しない DSL 仕様（仕様書 + JSON Schema）。全言語の共通ソース。
- **各言語版** … 同じ仕様を読んで、その言語で画面を実らせる。今は Flutter 版が動いてて、Java 版・TypeScript 版もこの上に乗せていく予定。

パッケージ名も揃える（Dart なら `hatake_core`、npm なら `@hatake/core`、Maven なら `io.github.asil-e-hatake:hatake-core` みたいに）。どの言語から入っても「あ、hatake ね」で通じるようにしたい。

## 設計として大事にしてること

力を抜いて書いてるけど、ここはちゃんとしてる。

- **Business First** — UI を作るんじゃなくて業務を記述する
- **Configuration over Coding** — 部品を書くより定義を書く
- **Backend Agnostic** — Repository インターフェースだけ知ってる。HTTP も DB も知らん（実装者の領分）
- **Renderer / Language Independent** — 描画も言語も交換可能
- **拡張は Plugin で** — フィールド型・バリデータ・アクション・描画そのものを、本体をいじらず足せる

特に描画層（Renderer）は**業務ロジックを持たない**。検索・ページング・CRUD・バリデーションみたいな状態管理は別の場所（コントローラ）に隔離してあって、Renderer は「状態を受け取って描くだけ」。だから丸ごと差し替えがきく。

## AI と相性がいい、というか狙ってる

定義の構造が単純で予測しやすいから、AI に「顧客マスタの CRUD 作って」って言ったら、Widget ツリーを推測させるんじゃなくて**この YAML を吐かせるだけ**で済む。人間が読みやすい形は、だいたい AI も書きやすい。

しかも DSL には JSON Schema と仕様書を付けてある。AI が吐いた定義はスキーマで機械検証できるから、typo や必須漏れはその場でエラーで返る＝AI が自分で直せる。エディタでもモデライン一行で補完が効く。

## いまの状態と、これから

Flutter 版で **CrudPage（登録・参照・更新・削除）** と **SearchPage（照会）** が動いてる。テストも解析も通してある。

これからやること:
- 他の業務コンポーネント（マスタ、ダッシュボード、詳細 …）
- 別デザインの Renderer（Fluent とか）
- **Java 版・TypeScript 版**（同じ種で育てる）

## まとめ

業務画面を毎回手で量産するの、そろそろやめていいと思う。業務を定義して、あとは各言語の畠に任せる。それが hatake。

## 命名について

なんで「畑」じゃなく「畠」なのか、って話。同じ「ハタケ」でも「畑」って字があるけど、あえて避けた。「畑」は字面に **火** が入ってて **焼き畑** のイメージが強い。で、プロジェクトやってて一番やらかしたくないのが **炎上**。縁起でもないから、火のない方にした（半分本気）。

選んだ「畠」は「白 + 田」、つまり **水を抜いた田んぼ**。地味だけど、これが潰しの効く土台なんだよね。

- 水を入れれば **米** が作れる
- そのまま使えば **麦や野菜** が作れる
- なんなら **二毛作・三毛作** までいける

要は「**基盤（畠）さえ動かなければ、上に載せるもの（作物）はいくらでも変えられる**」。これ、hatake の思想そのまんまなんだよね。定義の土台は堅く作っておくから、その上にどんな画面を実らせるかは自由、っていう。

作ってる側の気持ちとしてはこう:

> 焼け野原じゃない、ちゃんとした基盤はこっちで用意しとく。あとは農家（＝使う人や AI）がいい感じに耕して、good なものを育ててくれ。

そういうスタンスでやってる。🌱

### ……というのは半分後付けで（裏話）

ここまでそれっぽい理屈を並べてきたけど、正直に白状すると——**作者の苗字が「畠山」なんだよね**。要は「自分の名前がちょっと残るようなものを作りたい」ってのが最初にあって、そこから「畠」って字を使う口実として、上の田んぼの話を後付けでこしらえた、ってのが元も子もない本音。

まあ動機が名前でも、土台がちゃんとしてれば作物は実る。名前負けしないやつにしていければいいかな、と思ってる。
