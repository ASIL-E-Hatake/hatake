# 1.0 の約束（何を凍らせて、何を凍らせないか）

配ったら直せなくなるものを、配る前に決めておく1枚。

機能を足すのはいつでもできる（足しても誰も困らない）。困るのは**約束を後から狭める**ときで、
これは相手の CI と定義ファイルを壊す。だから「1.0 で何を約束するか」を先に書いておく。

**ここで言う「配る」はレジストリに出すことだけではない。** git の tag で配っても、
id と終了コードは相手の CI に埋まる＝同じように直せなくなる。違うのは1点だけで、
**git のうちは利用者を数えられるので、間違えても一斉に直せる**。だから git の期間は
「約束を先送りする期間」ではなく、**約束を入れて踏んでみる、いちばん安い期間**。

---

## 凍らせるもの

| | 中身 | 破るとどうなるか |
|---|---|---|
| **DSL のキー・スキーマ** | `spec/hatake-page.schema.json` に在るキーと値 | 相手の定義ファイルが落ちる |
| **DSL の版の扱い** | 下の「版」 | 別の版の定義を黙って読む |
| **診断の id** | 警告と助言の `rule`（[`spec/rule-ids.json`](../spec/rule-ids.json)） | 相手の CI の抑制・集計が壊れる |
| **終了コード** | 下の「終了コード」 | CI が黙って緑になる（いちばん見つからない） |
| **`--json` の形** | 出しているキーと意味 | 相手の道具が落ちる／黙って空を読む |
| **公開 API** | 各版が `index` から出しているもの | 相手のコードがコンパイルできなくなる |
| **パッケージ名・スキーマの `$id`** | 名前と URL | 相手の設定を全部書き換えさせる |

## 凍らせないもの（そう書いておく）

- **人に読ませる文面** — `explain` / `advise` / `ask` / `design` / `paper` / `probe` の日本語。
  読みやすくするために書き換える。**機械で食うなら `--json` を使う**（そっちは凍っている）
- **助言（好み）の規則の増減** — 助言は「書いていないと不便かも」で、終了コードを動かさない。
  効かない規則は切るし、要るものは足す。**id を使い回さない**（消した id を別の意味で復活させない）
- **MCP の道具の並びと `instructions`** — 使ってほしい順番は変わる
- **同梱の例・失敗例カタログの中身** — 増える

## DSL の版

**読めない版は落とす。** 詳しくは [DSL 仕様の「DSL の版」](../spec/dsl-spec.ja.md#dsl-の版dsl_version)。

- 知らない major（`2.0` / `0.9`）… **落とす**
- 同じ major の新しい minor（`1.1`）… **読むが1件言う**（`dsl-version-newer`）
- 形が違う（`1` / `1.0.0` / 空）… **落とす**
- 書いていない… 通す（既定は現在の版）

**minor は足すだけ**（キー・値・既定値を増やす）。**意味を変える・消すときは major を上げる。**
判定は3版＋スキーマで同じで、正は
[`spec/conformance/dsl_version.json`](../spec/conformance/dsl_version.json)。

## 診断の id

`hatake rules` で引ける警告と助言の `rule` は、**公開 API**。相手はこれを
`--warn-as-error` で落とし、grep で抑制し、集計する。

- **名前を変えない。消さない。** どちらも破壊的変更
- 足すのは自由。ただし [`spec/rule-ids.json`](../spec/rule-ids.json) に1行足すのが条件
  ＝意図した追加になる（試験が完全一致を見るので、減る差分はレビューで必ず目に入る）
- 要らなくなった規則は**消さずに出し続ける**。少なくとも1つの major は残す
- **id を使い回さない。** 消した id を別の意味で復活させるのがいちばん質が悪い
  （相手の抑制設定が、黙って別のものを抑制する）

いま凍っているのは**警告 94・助言 21**。

## 終了コード

| コード | 意味 |
|---|---|
| `0` | 問題なし（助言だけが出たときも `0`。助言は好みなので落とさない） |
| `1` | 落ちる問題（検証の失敗・使い方の誤り・読めないファイル・後方互換を壊す差分） |

いま使っているのはこの2つだけ。**`1` の意味は変えない。** 細かく分けたくなったら `2` 以降を
足す（足すのは互換）。

## `--json` の形

機械が食う形は、人が読む形とは別に凍らせる。

- **キーを足すのは互換**（相手は知らないキーを無視する前提で書く）
- **キーを消さない・意味を変えない**
- **型を変えない**（数だったものを文字列にしない）
- 空のときは**キーごと消さずに空の配列を出す**（「無い」と「答えられない」を区別する）

## 公開 API

各版が `index` から出しているものは、全部「約束」になる。うっかり内部の道具を出すと、
それも消せなくなる。

- TypeScript … **口が2つ**ある（下）
- Dart … `lib/src/` は言語の仕組みで隠れているので、`export` した分だけが約束
- Java … `io.hatake.core` の public が約束

### TypeScript は2つに分けてある

| 口 | 約束するか | 何が在るか |
|---|---|---|
| `@hatake-fw/api` | **する** | 手引きが名前で案内しているもの（35個＋型） |
| `@hatake-fw/api/internal` | **しない** | 枠組みの中身そのもの（588個） |

一覧は [`spec/public-api.ts.json`](../spec/public-api.ts.json)。試験が完全一致を
見るので、**約束の面が変わったら必ず目に入る**。

**なぜ分けたか。** `index.ts` が 142 モジュールを `export *` で丸ごと出していたので、
**内部に定数を1つ足すだけで約束が1つ増えて**いた（8日で 586 → 588。どちらも検証規則の
内部の表で、利用者が呼ぶものではない）。全部を約束すると、人に見せる字を良くするだけで
「約束を破った」ことになる。

かといって隠すと、枠組みの中身を使いたい人の道が消える。だから**道は残して、約束だけを
分けた**。`internal` は使えるが、名前も形も断りなく変わる。

約束する面に足すときの線引きは3つ（`typescript/src/index.ts` の頭にも書いてある）。
ひとつでも外れるなら `internal` に置く:

- **手引きが名前で案内している**（[サーバ側の使い方](guide/backend.ja.md#同じ定義を3つの用途で使う)の表）
- **呼ぶ相手が業務のコード**である（枠組みの中から呼ぶだけの道具ではない）
- **中身が変わっても名前と形が変わらない**と言い切れる

## 名前の決めごと

**名前空間＝誰が出しているか。名前＝役割。どこかに必ず `hatake` が出る。**

| | 名前空間 | 名前 | 例 |
|---|---|---|---|
| pub.dev | 無し | `hatake_<役割>` | `hatake_core` / `hatake_material` |
| npm | `@hatake-fw` | `<役割>` | `@hatake-fw/api` / `@hatake-fw/vue` |
| Maven | `io.github.asil-e-hatake` | `hatake-<役割>` | `hatake-core` |
| GitHub | `ASIL-E-Hatake` | `hatake` | |

**スコープに修飾語を付けない。** `@hatake-ui` や `@hatake-dsl` にすると、**必ず半分が嘘に
なる**（npm には Renderer・API のロジック・道具が同居する。`-ui` は API 版を、`-dsl` は
Renderer を、それぞれ名前で誤ラベルする）。無印の `hatake` は 2024 年に別人が取っていた
ので、**中立な修飾**（`-fw`）を付けて逃げた。

**Renderer は描画先の名前で呼ぶ**（`hatake_material` / `@hatake-fw/vue`）。
「どの Renderer か」は交換の単位そのものなので、名前がそれを言う。

### 役割の名前（版をまたいで同じ意味で使う）

| 役割 | pub.dev | npm |
|---|---|---|
| 定義モデル・解析・strict | `hatake_core` / `hatake_yaml` | `core` |
| DSL ビルダー | `hatake_dsl` | `dsl` |
| 描画 | `hatake_material` | `vue` / `react` |
| サーバ側のロジック（検証・クエリ・DTO） | （無し。Flutter は描画側） | `api` |
| HTTP | `hatake_http` | `http` |
| 帳票 | `hatake_print` | `print` |
| 画面の試験 | `hatake_test` | `test` |
| 道具（CLI / MCP） | （無し） | `cli` / `mcp` |

**いま npm に在るのは `@hatake-fw/api` 1つ**で、解析も道具も全部その中に入っている。
Renderer（`vue` / `react`）を足す段で `core` を切り出し、`api` は `core` に依存する形にする
＝`api` が今の export をそのまま再 export すれば、**利用者側は壊れない**（後から割っても
互換になるように、最初から `core` とは名乗らない）。

### 名前の状態

| | 状態 |
|---|---|
| npm `@hatake-fw` | **確保済み**。無印 `hatake` は他人のもの（2024 年の別パッケージ）、`@hatake` スコープも取得不可 |
| npm `@asil-e-hatake` | 確保済み（保険。使っていない） |
| pub.dev | 9つ全部空き。**予約の仕組みが無い**ので、押さえるのは publish のとき |
| Maven | `io.github.asil-e-hatake` は GitHub アカウントの所有で自動検証＝確保済み |

## 版の足並み

**3版は同じ番号で出す**（Flutter / TypeScript / Java）。

収束テスト（`parse(YAML) == parse(JSON) == build(DSL)`）で3版が同じ答えを出すことを
保証している以上、番号がバラけるとその保証が読めなくなる（「Flutter 1.2 と TS 0.8 は
組み合わせていいのか」に誰も答えられない）。

**DSL の版（`dsl_version`）はパッケージの版とは別**。DSL は仕様の版で、パッケージは実装の版。
実装を直しただけで DSL の版は上がらない。

## 約束を破る必要が出たとき

1. まず**足して済まないか**を考える（新しいキー・新しい id・新しい終了コード）
2. 済まないなら **major を上げる**
3. 消す側は**すぐ消さない**。deprecated として1つの major は残し、使われたら言う
