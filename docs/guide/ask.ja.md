# 決めていないことを問い返す（hatake ask）

雑な依頼から画面を起こすと、**書けることは全部書ける**。だから出来上がった定義には
空欄が無い。空欄が無いと、決まっていないようには見えない。

そして動かした後にこう言われる。

- 「2人で同時に直したらどうなるの」
- 「消したやつって残ってるの」
- 「この端数、切り捨てでいいんだっけ」

**全部、定義に書けないこと**だ。だから `validate` も `advise` も言えない（あの2つは
定義に書けることしか見ない）。ここだけが抜ける。

```bash
npx hatake ask spec/pages/order_entry.yaml
```

```text
決めてください（2件）。

必ず決めること（2件）

1. [concurrency] 同じ1件を2人が同時に直したら、どちらの入力を残しますか（後から押した人を通す／弾いて読み直させる）。
   聞く理由: 定義に書けるのは「入力できる」までで、**誰の入力が残るか**は保存する側の話。
   決めないと: 先に保存した人の入力が黙って消える。しかも画面には両方とも「保存しました」と出る。
   誰の担当か: サーバの担当
   答えの書き方: `logic` に1行（`what: 受注は更新日時が変わっていたら弾いて読み直させる` / `where: server`）。
   この定義で聞いた理由: order_entry: 保存できる画面（type: form）
```

## 3つを混ぜない

| | 何を言うか | CI で落とすか |
| --- | --- | --- |
| 警告（`validate`） | **書いたのに効かない**。事実 | 落としてよい |
| 助言（`advise`） | **書いていないと不便かもしれない**。好み | 落としてはいけない |
| 問い（`ask`） | **定義に書けない**のに、決まっていないと画面が嘘になる | 落とさない（人への依頼なので） |

問い返しが**終了コードを変えない**のはここが理由。問いは機械の合否ではなく、人への
依頼だ。落とすと「答えるまで CI が赤い」＝答えを適当に書く圧力になる。

## 聞くのは「定義に書けないこと」だけ

表に載せる条件はひとつしかない。**定義に書けないこと**。

書けるなら助言の担当なので、各件には[担当の区分](concepts.ja.md#これはどっちの担当は引ける)が
付いていて、**`server` と `outside` しか書けない**（`definition` や `plugin` の担当を
問いにしようとすると、道具が落ちる）。同じことを2か所で言わないための仕掛けで、
言い換えると**この表は「枠組みが持たないもの」の裏返し**になっている。

いま聞くのは 12 種類。

| 印 | 聞くこと | 引き金（定義の事実） |
| --- | --- | --- |
| `concurrency` | 同時に直したらどちらを残すか | 保存できる画面が在る |
| `numbering` | 新しい1件の番号は誰が付けるか | `type: create` のボタンが在る |
| `erase` | 消したものを残すか | `type: delete` が在る |
| `partial-failure` | 一括が途中で落ちたら | 選んだ行にまとめて実行するボタンが在る |
| `validation-server` | 同じ検証をサーバでも見るか | `required` か `validators` が在る |
| `authz-server` | 隠したものをサーバでも止めるか | `roles` が在る |
| `role-source` | 役割はどこから来るか | `roles` が在る |
| `rounding` | 端数をどう扱うか | `avg` / `product` で計算している |
| `state-owner` | その状態は誰が動かすか | `enabledWhen` などで出し分けている |
| `audit` | 誰が何をしたかを残すか | `type: delete` が在る |
| `report-source` | 帳票の数字はいつの値か | `type: report` が在る |
| `notify` | 動かしたあと誰かに知らせるか | 選んだ行にまとめて実行するボタンが在る |

表そのものは定義が無くても引ける。**書く前に、何を聞かれるか**が分かる。

```bash
npx hatake ask --kinds
```

## 思いついたことは聞かない

1件ごとに「この定義で聞いた理由」が付く。どの画面の何を見てその問いを出したか、だ。

これが無い道具は使われなくなる。毎回違うことを聞かれると、3回目から読まないので。
だから問いは**必ず定義の事実から出す**（引き金は9つの閉じた集合で、名前から推測する
引き金は1つも無い＝「金額らしいから端数を聞く」はやらない）。

## 答えたら消える

答えの置き場所は[案件の前書き](project.ja.md)の `logic`。その1行に `answers` を付ける。

```yaml
project_version: "1.0"
system:
  what: 卸売の受注。営業が電話で受けた注文を入れる。
logic:
  - what: 受注は更新日時が変わっていたら弾いて、読み直させる（後勝ちにしない）
    where: server
    answers: [concurrency]
```

次からその問いは出ない。**消えることが大事**で、消えない問いは穴の在り処が間違って
いる（そこは試験が見ている＝12 種類を1つずつ答えて、1つずつ消えることを確かめている）。

辻褄が合わない答えは受け取らない。ここだけは**落とす**（問いが出たことでは落とさない
のに、ここで落とすのは、これが好みではなく事実の間違いだから）。

- 知らない印を書いた（`answers: [no-such-question]`）
- 担当が食い違う（排他はサーバの担当なのに `where: definition` と書いた）

### 既定のままでよい、と決めたとき

答えを書くほどでもない（既定のままでよい）と決めることもある。それは `logic` に書く
ことが無いので、`questions.decided` に理由つきで残す。

```yaml
project_version: "1.0"
system:
  what: 卸売の受注。営業が電話で受けた注文を入れる。
questions:
  decided:
    - id: notify
      why: 却下は同じ画面を見ている担当が拾うので、外へ知らせる口は要らない
      date: "2026-09-14"
```

**理由は必須**。`where: outside` と同じ考えで、理由が無いと「なぜ聞かれなくなったのか」
が消えて、後から誰も直せない。

答え（`answers`）と「決めた」（`decided`）を**両方書くことはできない**。どちらが本当か
分からなくなるので、道具が落とす。

消した件数は黙らない。報告の1行目に「前書きで答えが済んでいるもの 1件・既定のままで
よいと決めたもの 1件」と出る＝**聞かれなかったのか、決めたから消えたのか**が読める。

## この案件でしか出ない決めごとを足す

組み込みの12種類は「業務システムで大抵決めていないこと」なので、会社ごとの決めごと
（稟議番号の採番規則・保存期間）は入っていない。足せる。

```yaml
project_version: "1.0"
system:
  what: 卸売の受注。営業が電話で受けた注文を入れる。
questions:
  ask:
    - id: retention
      step: must
      where: outside
      trigger: saves
      ask: この画面で入れたものは何年残しますか。
      why: 保存期間は業務と法律の決めごとで、定義には書けない。
      ifNot: 消してよいものが分からず、結局ずっと残ることになる。
      answer: logic に1行（受注は7年保存 / where outside）。
```

読み手は**組み込みと同じ**なので、案件の紙にだけ緩い形は書けない。

| 縛り | なぜ |
| --- | --- |
| `where` は `server` か `outside` だけ | 定義やアプリ側で書けることは、問いではなく[助言](../../typescript/README.md#advise)の担当 |
| `trigger` は決まった9つ | 問いは**定義の事実**から出す（思いついたことは聞かない） |
| 印は組み込みとぶつけられない | 上書きを許すと、`answers: [erase]` がどちらへの答えか分からなくなる |

条件式は書けない（書けるようにすると問いの DSL になる）。出るときは印に
**（この案件の決めごと）**が付くので、読む人は組み込みと区別できる。

## 触る前に聞く

「この項目もう要らないんだけど、消していい？」に答えるには、**他の画面で使っていないか**
を辿る必要がある。定義が10枚を超えると人の頭では追えない。

```bash
npx hatake ask spec/pages/order_entry.yaml --impact price
```

```text
"price" を触ると、定義の 3 か所に響きます。

どうしますか（消す／名前を変える／残して画面から隠す）。

一覧の列です（消すと、その列が画面から消えます）:
  ・order_entry: page.form.sections[1].fields[0].columns[2].field（単価）

**計算の元**です（消すと、その計算の答えが変わります）:
  ・order_entry: page.form.sections[1].fields[0].fields[3].computed.fields[1]（金額）
```

辿るのはこの8つ。**明細（`subTable`）の中まで開く**（「明細の単価を消したい」が一番多い）。

| 種類 | 何が壊れるか |
| --- | --- |
| キー | 1件を指せなくなる（編集・削除・遷移が全部） |
| 列 / 絞り込み / 入力欄 | 画面からその項目が消える |
| 計算 | 計算の答えが変わる（`fields` / `field` / `of` / 行を絞る `where` も見る） |
| 条件 | 出し分けの判定が壊れる（`visibleWhen` / `enabledWhen` / `readOnlyWhen` / `requiredWhen`） |
| 遷移のパラメータ | 受け取る側に値が届かない（`$row.<項目名>`） |
| 帳票 | 合計・並び・まとめが変わる |

**定義に無い名前は「影響なし」と言わない。** 打ち間違いを見て消されると困るので、
「定義のどこにも出てきません」と言って 1 を返す。

辿るのは**この定義の中だけ**。サーバが返している項目・プラグインの中身・アプリの
ハンドラ・試験は見えないので、毎回そう言う（「他に影響はありません」とは言わない）。

## 決めていないことを PR に貼る

決めていないことは**レビューの席でこそ**答えが出る（その場に業務の人が居る）。人が
叩いたときだけ出るのでは、その席に届かない。

```bash
npx hatake ask app.yaml --markdown
```

表と畳んだ塊（`<details>`）で出るので、そのまま PR のコメントに貼れる。**囲みの字は
1つも出さない**＝貼った先が手引きやワークフローの断片だと、囲みが入れ子になって
塊を抜き出す側が途中で切れるので（[前にやった](../index.ja.md)）。

答えが前書きに入れば、その問いは次から出ない＝**同じ問いが増え続けない**。

## 会社の決めごとを、案件をまたいで渡す

保存期間・稟議番号の採番規則のような**会社の決めごと**は、案件をまたぐ。前書きに
写すと写した先が古くなるので、1枚を渡す。

```bash
npx hatake ask app.yaml --questions team.json
```

中身は前書きの `questions.ask` と同じ形（`{ "kinds": [ … ] }`）。並びは
**組み込み → 会社 → 案件**で、どこで印がぶつかっても落ちる（どちらが正かは道具が
決めない）。出た問いには「（会社の決めごと）」「（この案件の決めごと）」が付く。

## 雑な依頼から、ここまでの3手

`ask` は定義を読む道具なので、依頼文を直接は読まない（**書いていないことは責められ
ない**ので、指示文からは事実が取れない）。実際はこう回す。

```bash
npx hatake where --from 依頼.md          # 1. 仕分ける（枠組みの外が混ざっていたら先に言う）
npx hatake new crud --out order.yaml     # 2. 書けるものを書く
npx hatake ask order.yaml                # 3. 書けなかったことを人に聞く
```

AI に投げるなら [MCP](mcp.ja.md) の `hatake_ask`。**返ってきた問いは人に投げること**＝
当てて書いてはいけない。答えは業務の判断なので、推測で埋めると「決まっているように
見える嘘の設計」ができる。いちばん質が悪い。

## 見ていない所

毎回そう言う。

- **出なかった＝決まっている、ではない。** 表に無いことは聞かない
- **答えが正しいかは誰も見ていない。** 前書きの `logic` に書いた1行が本当にサーバで
  守られているかは、定義からは分からない（[読み返し](project.ja.md#機械が見るのは名前だけ)が
  同じことを言う）
- **問いの数は設計の良し悪しではない。** 保存する画面が在れば排他は必ず聞かれる
