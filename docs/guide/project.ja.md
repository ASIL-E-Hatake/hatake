# 案件の前書き（AI に先に読ませる1枚）

> **中身**: この案件は何のシステムで、何ができないか、業務の言葉をどう書くか、名前をどう付けるかを1枚にして、定義を書く**前**に読ませる。
> **読むとき**: 新しい案件を始めるとき。2枚目の画面を頼むたびに同じ説明をしていると気づいたとき。

いきなり「〇〇画面を作って」と頼むと、AI は**書ける方に倒す**。商品マスタを直せない案件なのに編集ボタンが付いた画面が出てくるし、「取引先」と呼んでいるものが `customer` になる。悪気があるわけではなく、**どこにも書いていない**から。

定義には「何ができるか」しか書けない。**できないこと・呼び方・名前の付け方**は書く場所が無いので、その1枚を別に持つ。

## 置く

定義の隣に `hatake.project.yaml` を置く。名前がこれなら、道具は**渡さなくても読む**（`hatake-registry.json` と同じ）。

```yaml
project_version: "1.0"

system:
  what: 卸売の受注。営業が電話で受けた注文を入れて、出荷指示まで出す。
  users:
    - 営業（10人・事務所の PC）
    - 出荷担当（倉庫のタブレット。手袋のまま触る）
  premises:
    - 商品マスタは購買部の別システムが正。こちらからは直せない（照会だけ）。
    - 締めは月末。締めたあとの受注は直せない。
  external:
    - name: productRepository
      what: 商品マスタ（購買システムの REST）
      owner: 購買部

glossary:
  - term: 取引先
    field: partnerCode
    avoid: [顧客, 得意先]
    note: 社内の帳票が全部「取引先」なので、画面もそう呼ぶ

naming:
  page: snake_case
  field: camelCase
  action: camelCase
  repository: camelCase
  role: snake_case
  suffix:
    date: Date
```

読み返しはこれ。

```bash
npx hatake project                     # 隣の hatake.project.yaml を読む
npx hatake project team/wholesale.project.yaml --json
```

## 何を機械が見て、何を見ていないか

ここが肝心なところで、**読み返しが毎回言う**。

| 書いたもの | 誰が見るか |
| --- | --- |
| `system`（何のシステムか・使う人・前提・外の相手） | **人と AI が読むだけ**。誰も突き合わせていない |
| `glossary`（用語辞書） | `hatake advise --project` がラベルと項目名を突き合わせる |
| `naming`（名前の決めごと） | `hatake advise --project` と `hatake new --project` |

前書きを渡すと「これで縛れた」と思ってしまうが、**前提は縛れていない**（定義に書きようがないので）。縛れているのは名前と言葉だけ。そこを黙ると、見ていないものを見ているように見せることになる。

## 名前と言葉を突き合わせる

```bash
npx hatake advise page.yaml --project hatake.project.yaml
```

`project-` で始まる助言が出る。

```
# page.search.filters.0 [project-name-suffix]
  こうなる: `type: date` の項目 "orderDay" は、案件の決めごとでは名前を "Date" で終わらせます。
  書き足す: "Date" で終わる名前に直す（決めごと: naming.suffix.date = Date）。

# page.table.columns.1 [project-glossary-word]
  こうなる: ラベル「顧客コード」に「顧客」が入っています。案件の決めごとでは「取引先」と呼びます（社内の帳票が全部「取引先」なので、画面もそう呼ぶ）。
  書き足す: 「取引先」で言い直す。
```

見るのは4つ。

- **名前の形**（`naming.page` / `field` / `action` / `repository` / `role`）。`ProductSearch` は snake_case の案件では言われる
- **型に合わない終わり方**（`naming.suffix`）。`type: date` なのに `orderDay` で終わっている
- **呼ばないことにした言葉**（`glossary[].avoid`）。ラベルに「顧客」が出てきた
- **辞書の言葉なのに、名前が辞書から来ていない**（`glossary[].field`）。これは**名前からの推測**なので、そう書いてある＝「取引先名」に `partnerName` と付けるのは正しいので、辞書の名前と完全一致では見られない。辞書の名前の**最初の語**が入っているかを見ている

同じ名前は絞り込み・列・入力欄の3か所に出るので、**1件にまとめて「他に2か所」と言う**（3件並べても読めないが、直す範囲は知りたい）。

これは**警告ではなく助言**。名前と言葉は「書いたのに効かない」ではなく**案件の好み**なので、終了コードは変えない。合わない決めごとは物差しの `off` で止められる（[助言の物差し](advise-rules.example.json)と同じ書き方）。

**`--apply` では当てられない。** 項目名を書き換えると、その名前で話している所（Repository・API・試験・別の画面の遷移）まで一緒に直さないと壊れるので、道具は「当てられません」と言って止まる。

レビュー用の1枚（`explain --review`）にも同じものが載る。

```bash
npx hatake explain page.yaml --review --markdown
```

`advise` では出るのに `--review` では出ないと、1枚を読んだ人は「言われていない」と読むので、
出す所は揃えてある。

## 雛形を案件の形で出す

```bash
npx hatake new crud --id order_entry --title 受注入力 --project hatake.project.yaml
```

雛形が出す**業務の名前**が決めごとの形になる（DSL のキーは触らない＝`pageSize` は枠組みが決めた字なので、案件の決めごとの外）。

**渡した `--id` は書き換えない。** 頼んだ字と違うものが出るほうが困るので、決めごとに合っていなければ「合っていません」と言うだけにしてある。

## AI に読ませる

MCP を繋いでいれば `hatake_project` が同じ1枚を読む。道具の順番は**これが最初**で、次が「言われたことを1枚にする」（`hatake_intent`）。

繋いでいないなら、最初の1往復で `npx hatake project` の出力をそのまま貼るのでも効く（読み返しの形は人にも AI にも同じものを渡している）。

## AI の設定ファイルに貼る

MCP を繋がない使い方（Copilot・Cursor・ふつうのチャット）だと、AI に渡る前置きは
`AGENTS.md` や `CLAUDE.md` に書くことになる。そこに同じことを手で書くと、**前書きを
直したのに設定ファイルが古い**が必ず起きる。なので**1枚を正にして、貼る側を生成する**。

```bash
npx hatake project --agents                      # 貼る断片（印つきの Markdown）
npx hatake project --agents --merge AGENTS.md    # 2回目以降：印の中だけを差し替える
npx hatake project --agents --merge AGENTS.md --check   # CI：貼った節が古くないか
```

出るのはこういう形。

```markdown
<!-- hatake:project:begin -->
## この案件について

> ここは `hatake.project.yaml` から生成した節です（`npx hatake project --agents`）。
> **直すときは前書きを直して貼り直す**（同じことを2か所に書くと必ず食い違う）。

卸売の受注。営業が電話で受けた注文を入れて、出荷指示まで出す。
...
<!-- hatake:project:end -->
```

決めごとは3つ。

- **印（`hatake:project:begin` / `end`）の中だけ**を差し替える。`--merge` は印の外を触らない
- **印が無ければ書かない。** どこに入れるかはその紙を書いた人が決めることなので、1回目は
  人が貼る（`--merge` なしで出して、印ごと貼る）
- **ブランチ名・コミット規約は印の外に手で書く。** 前書きが持たないものは生成に含まれない
  ので、印の外に置いておけば貼り直しても消えない

`--check` は書かずに**古くなっていないか**だけを見る（違えば終了コード 1）。生成物なのに
古い節が貼ってあると、AI はそれを読む＝前書きを直した意味が消えるので、CI に1行置いておく。

貼った断片にも「**業務の前提は機械が見ていない**」と書いてある。設定ファイルに前提が
載っていると「守られている」と読まれるので、そこだけは毎回断っておく。

## ここに書かないもの

**ブランチ名・コミット規約・レビューの回し方・ディレクトリの切り方**は書かない。定義に現れないので機械が突き合わせられず、書いても腐る（誰も見ていない散文になる）。そちらは `AGENTS.md` / `CLAUDE.md` の担当で、hatake は**定義に現れるものだけ**を持つ。

**前書きを定義から生成してもいけない。** 生成すれば必ず一致するので、突き合わせが何も言わなくなる（[言ったことを残す1枚](../../spec/intents/product_search.intent.yaml)と同じ理由）。書くのは人。

## 意図の1枚との違い

似た紙が2枚あるので、分けて覚える。

| 紙 | 何が書いてあるか | いつ書くか |
| --- | --- | --- |
| 案件の前書き（`hatake.project.yaml`） | **案件ぜんたい**の話。何のシステムか・用語・名前 | 案件の最初に1回。あとは足していく |
| 意図の1枚（`<画面id>.intent.yaml`） | **画面1枚**の話。言われたこと・決めごと・未決 | 画面を作るたび |

前書きは「どう書くか」、意図は「何を言われたか」。突き合わせる相手も違う（前書きは名前と言葉、意図は定義の項目とボタン）。
